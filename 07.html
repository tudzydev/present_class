Feeling ยอดปิดบัญชีที่ไม่ตรงของร้านสวัสดิการ

สัปดาห์สอบสุดท้าย ร้านสวัสดิการนักศึกษามียอดขายพุ่ง แต่ตอนปิดบัญชีกลับ เงินขาดหายทั้งสัปดาห์ ตรวจสอบพบว่าพนักงานพาร์ทไทม์แก้ “จำนวนชิ้น” ในคำสั่งซื้อของลูกค้าประจำเพื่อแถมของฟรี โดยที่ระบบไม่ทักท้วงเลย ที่ซ้ำร้ายกว่านั้น “ส่วนลดนักศึกษา 10%” ถูกเขียนตายไว้ในคลาส Order สภานักศึกษาอยากเปลี่ยนโปรโมชันเป็น “ครบ 300 ลด 20” จึงทำไม่ได้ถ้าไม่แก้โค้ดทั้งก้อน — และไม่มีใครกล้าแก้ช่วงสอบสุดท้าย

1) คุณรู้สึกอย่างไรกับเรื่องนี้ และระหว่าง “คนที่แอบแก้ข้อมูล” กับ “ระบบที่ยอมให้แก้ได้” คุณคิดว่าใครควรรับผิดชอบมากกว่ากัน เพราะเหตุใด

2) การที่ “สูตรส่วนลด” ถูกฝังตายไว้ใน Order สร้างความเจ็บปวดให้ใครบ้าง เมื่อธุรกิจอยากเปลี่ยนโปรโมชัน

เรื่องเล่าจากพี่เลี้ยง: “วันที่แคมเปญ 3 ตัวตีกันในโค้ดเดียว”

พี่เก่ง — Senior Engineer ทีม e-commerce เล่าว่าโค้ดเก่ามีสูตรส่วนลดทุกแบบ (โค้ด 10%, สมาชิก 15%, แคมเปญ 20%) ฝังเป็น if-elif ยาวเหยียดในคลาส Order วันที่ฝ่ายการตลาดยิง 3 แคมเปญพร้อมกัน สูตรตีกันเอง ระบบคิดส่วนลดผิดหลายพันคำสั่งซื้อ บริษัทชดใช้หลักล้านบาท หลังวิกฤตเขา refactor แยก “นโยบายส่วนลด” แต่ละแบบเป็นคลาสอิสระ ที่เสียบเข้า Order ผ่าน constructor ตั้งแต่นั้นการเพิ่มแคมเปญใหม่ใช้เวลาไม่ถึงชั่วโมง และทีมการตลาดไม่ต้องรอคิวโปรแกรมเมอร์อีกเลย “ของที่เปลี่ยนบ่อยที่สุด ต้องอยู่ห่างจากของที่ไม่ควรเปลี่ยนที่สุด”

ถอดรหัสวิธีคิดของคนสำเร็จ:

  • ประกอบระบบจากวัตถุเล็ก ๆ (Composition) แทนการสร้างลำดับชั้นสืบทอดที่เปราะบาง
  • แยก “สูตร/นโยบาย” ที่เปลี่ยนบ่อยออกเป็น Strategy ภายใต้ interface เดียว
  • ให้คนที่ถือข้อมูลเป็นผู้คำนวณเอง (Information Expert) — OrderItem รู้ quantity/price จึงคำนวณ total เอง

Finding Sandbox: Order ที่ทั้ง “แก้ได้” และ “รู้มากไป”

ทัศนคติประจำใบงาน: Failure is learning — ผิดหรือถูกไม่สำคัญ นี่คือการทดลองเพื่อเติบโต

พิจารณาโค้ดต่อไปนี้ แล้วสังเกตว่าความผิดพลาดสองแบบซ้อนทับกันอย่างไร

class Order:
    def __init__(self):
        self.items = []   # ใครก็แก้ list ได้!

    def total(self) -> float:
        s = sum(i['quantity'] * i['unit_price'] for i in self.items)

        # ส่วนลดถูก hardcode ไว้ใน Order!
        if s >= 300:
            s -= 20
        return s * 0.90   # ส่วนลดนักศึกษา 10% ถูกใช้เสมอ


order = Order()
order.items.append({'quantity': 2, 'unit_price': 60})
order.items[0]['quantity'] = -99   # ใครก็แก้รายการได้!
print(order.total())

1) ผลลัพธ์ที่ออกมาน่าแปลกใจอย่างไร และช่องโหว่ใดบ้างที่คุณพบ (ทั้งด้านข้อมูลและด้านนโยบาย)

2) คุณจะออกแบบอย่างไรให้ (ก) รายการสั่งซื้อถูกแอบแก้ไม่ได้ และ (ข) Order ไม่ต้องรู้จักสูตรส่วนลดแม้แต่สูตรเดียว

3) ลองให้ AI เสนอวิธีแยกนโยบายส่วนลดออกจาก Order มา 3 วิธี แล้วถกกับเพื่อน: วิธีใดน่าเชื่อถือที่สุด และคำตอบของ AI เชื่อถือได้มากน้อยเพียงใด (ฟังเพื่อนให้จบก่อนสรุปนะ)

📦 กล่องความรู้เสริม (อ่านเฉพาะเมื่อจำเป็น):
  • Composition over Inheritance: ประกอบพฤติกรรมจากวัตถุเล็ก ๆ แทนลำดับชั้นสืบทอดที่เปราะบาง
  • Strategy Pattern: แยก “สูตร/นโยบาย” ที่เปลี่ยนบ่อยเป็นคลาสอิสระภายใต้ ABC เดียว
  • Information Expert (GRASP): ผู้ถือข้อมูลควรรับผิดชอบการคำนวณ — OrderItem มี quantity/unit_price จึงคำนวณ total() เอง
  • Validation ตอนสร้าง: ไม่ยอมให้สร้างรายการที่ผิด (quantity ≤ 0, ราคาติดลบ, ชื่อว่าง) ด้วย __post_init__
  • frozen dataclass: คำสั่งซื้อที่สร้างแล้วต้องไม่ถูกแอบแก้ — ยอดรวมจึงเชื่อถือได้

ส่วนที่ 1: อ่านแผนภาพแล้วตอบคำถาม (10 คะแนน)

1) สัญลักษณ์สี่เหลี่ยมทึบ (composition) ด้าน Order ของความสัมพันธ์กับ OrderItem หมายถึงอะไร แตกต่างจาก aggregation อย่างไร 2 คะแนน

2) เหตุใด OrderItem จึงเป็น «dataclass frozen» การออกแบบนี้ดีต่อระบบคำสั่งซื้ออย่างไร 2 คะแนน

3) ลูกศร “injected” จาก Order ชี้ไปยัง DiscountPolicy สื่อความหมายว่าอย่างไร 2 คะแนน

4) ลูกศร “implements” จาก PercentageDiscount ไปยัง DiscountPolicy หมายถึงอะไร หากเพิ่มส่วนลดแบบจำนวนเงินคงที่ (FixedDiscount) ต้องแก้โค้ดส่วนใดบ้าง (OCP) 2 คะแนน

5) ลูกศร “raises” จาก OrderItem ชี้ไปยัง ValueError หมายถึงการตรวจสอบเงื่อนไขใดบ้าง 1 คะแนน

6) เมธอด subtotal() และ total() ของ Order แตกต่างกันอย่างไร 1 คะแนน

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass(frozen=True)
class OrderItem:
    name: str
    quantity: int
    unit_price: float

    def __post_init__(self) -> None:
        if not self.name.strip():
            raise ValueError("Item name cannot be empty.")
        if self.quantity <= 0 or self.unit_price < 0:
            raise ValueError("Invalid order item.")

    def total(self) -> float:
        return self.quantity * self.unit_price


class DiscountPolicy(ABC):
    @abstractmethod
    def discount(self, subtotal: float) -> float: ...


class PercentageDiscount(DiscountPolicy):
    def __init__(self, percent: float):
        if percent < 0 or percent > 100:
            raise ValueError("Percent must be between 0 and 100.")
        self._percent = percent

    def discount(self, subtotal: float) -> float:
        return subtotal * self._percent / 100


class Order:
    def __init__(self, items: list[OrderItem], discount_policy: DiscountPolicy):
        self._items = list(items)
        self._discount_policy = discount_policy

    def subtotal(self) -> float:
        return sum(item.total() for item in self._items)

    def total(self) -> float:
        sub = self.subtotal()
        return round(sub - self._discount_policy.discount(sub), 2)


order = Order(
    [OrderItem("ข้าวผัด", 2, 60.00), OrderItem("น้ำดื่ม", 2, 10.00)],
    PercentageDiscount(10.0),
)
print(f"ยอดสุทธิร้านสวัสดิการนักศึกษา: {order.total():.2f} บาท")

1) โค้ดบรรทัดใดแสดงให้เห็นว่า Order “ไม่รู้รายละเอียด” ของนโยบายส่วนลด จงอธิบาย 2 คะแนน

2) จงคำนวณยอดสุทธิของคำสั่งซื้อในโค้ด (ข้าวผัด 2 × 60, น้ำดื่ม 2 × 10, ส่วนลด 10%) พร้อมแสดงวิธีทำ 3 คะแนน

3) การสร้าง OrderItem('', 1, 50) และ OrderItem('ปากกา', 0, 20) จะเกิดอะไรขึ้นแต่ละกรณี เพราะเหตุใด 3 คะแนน

4) เหตุใดการตรวจสอบค่าใน frozen dataclass จึงอยู่ใน __post_init__ แทน __init__ 2 คะแนน

ส่วนที่ 5: สะท้อนคิดเชิงออกแบบ OOAD (6 คะแนน)

1) การใช้ composition แทน inheritance ในการประกอบ Order จาก OrderItem มีข้อดีอย่างไร จงยกตัวอย่างสถานการณ์ที่ inheritance จะทำให้การออกแบบแย่ลง 2 คะแนน
