Feeling วันสุดท้ายของการชำระค่าเทอม

ระบบชำระค่าเทอมของมหาวิทยาลัยรองรับเฉพาะบัตรเครดิต นักศึกษาจำนวนมากที่ไม่มีบัตร ต้องยอมยืมบัตรเพื่อนมาจ่ายอย่างทุลักทุเล ฝ่ายการเงินขอให้เพิ่ม PromptPay แต่โปรแกรมเมอร์ตอบว่า “โค้ดมันพันกันอยู่ แก้แล้วต้องเทสต์ทั้งระบบ ขอเวลา 2 สัปดาห์” — เกินกำหนดชำระพอดี สุดท้ายนักศึกษาต้องจ่ายค่าปรับทั้งที่ความผิดไม่ใช่ของพวกเขา

1) คุณรู้สึกอย่างไรกับเรื่องนี้ และใครบ้างที่รับผลจาก “โค้ดที่เปลี่ยนไม่ได้” ทั้งที่ไม่ได้เป็นคนเขียนโค้ด

2) ถ้าคุณเป็นเจ้าของระบบ คุณจะกลัวอะไรมากกว่ากัน ระหว่าง “โค้ดยาวขึ้น” กับ “โค้ดที่แก้ทีไรพังทุกที” เพราะเหตุใด

เรื่องเล่าจากพี่เลี้ยง: “คืนที่เพิ่มช่องทางชำระเงินไม่ทัน”

พี่แบงค์ — Senior Engineer ทีม e-commerce เล่าว่าโค้ดเก่ามี if type == 'credit': ... elif type == 'promptpay': ... กระจายอยู่กว่า 40 แห่ง วันที่ผู้บริหารบอกว่า “พรุ่งนี้ต้องรับ TrueMoney” ทีมต้องอยู่กันทั้งคืนและยังพังไป 3 จุด หลังจากนั้นเขา refactor ให้ทุกช่องทางเป็นคลาสอิสระที่เสียบเข้า Gateway ผ่าน constructor ตั้งแต่นั้นการเพิ่มช่องทางใหม่ใช้เวลาไม่ถึงครึ่งวัน และไม่มี regression อีกเลย “จงแยกของที่เปลี่ยนบ่อย ออกจากของที่ไม่ควรเปลี่ยน”

ถอดรหัสวิธีคิดของคนสำเร็จ:

  • ห่อ “จุดที่เปลี่ยนบ่อย” (ช่องทางชำระเงิน) ไว้หลัง abstraction ที่มั่นคง (Protected Variations)
  • รับ dependency จากภายนอก ไม่สร้างเองภายใน (Dependency Inversion)
  • ทำให้ “การเพิ่มพฤติกรรมใหม่” = การเพิ่มคลาสใหม่ ไม่ใช่การแก้โค้ดเดิม (Open/Closed)

Finding Sandbox: Gateway ที่รู้มากไป

ทัศนคติประจำใบงาน: Failure is learning — ผิดหรือถูกไม่สำคัญ นี่คือการทดลองเพื่อเติบโต

พิจารณาโค้ดต่อไปนี้ แล้วจินตนาการว่ามหาวิทยาลัยเพิ่งเซ็นสัญญากับ TrueMoney Wallet

class PaymentGateway:
    def checkout(self, type_: str, amount: float) -> str:
        if type_ == 'credit':
            return f"ชำระ {amount:.2f} บาทด้วยบัตรเครดิต"
        elif type_ == 'promptpay':
            return f"ชำระ {amount:.2f} บาทด้วย PromptPay"
        # แล้ว TrueMoney ล่ะ? ต้องกลับมาแก้โค้ดชุดนี้อีก!
        return 'ไม่รองรับช่องทางนี้'

1) หากเพิ่ม TrueMoney Wallet โค้ดส่วนใดต้องถูกแก้ไข และความเสี่ยงของการแก้โค้ดเดิมคืออะไร

2) คุณจะออกแบบอย่างไรให้ Gateway “ไม่ต้องรู้จัก” วิธีชำระเงินแม้แต่ชนิดเดียว แต่ยังเรียกเก็บเงินได้ถูกต้อง

3) ลองให้ AI เสนอวิธีกำจัด if-elif ในโค้ดนี้มา 3 วิธี แล้วถกกับเพื่อน: วิธีใดน่าเชื่อถือที่สุด และคำตอบของ AI เชื่อถือได้มากน้อยเพียงใด (ฟังเพื่อนให้จบก่อนสรุปนะ)

📦 กล่องความรู้เสริม (อ่านเฉพาะเมื่อจำเป็น):
  • Strategy Pattern: แยกพฤติกรรม (วิธีชำระ) ออกเป็นคลาสอิสระที่สลับเปลี่ยนได้ภายใต้ ABC เดียว
  • Dependency Injection: รับ dependency ผ่าน constructor จากภายนอก ไม่สร้างเองภายในคลาส
  • DIP: คลาสระดับสูง (Gateway) พึ่งพา abstraction (PaymentMethod) ไม่ใช่ concrete class
  • Protected Variations: ห่อหุ้ม “จุดที่เปลี่ยนบ่อย” (ช่องทางชำระ) ด้วย interface ที่มั่นคง
  • GRASP Controller: Gateway เป็นผู้ประสานงานของ use case การชำระเงิน

ส่วนที่ 1: อ่านแผนภาพแล้วตอบคำถาม (10 คะแนน)

1) «ABC» PaymentMethod ที่มีเมธอด +pay(amount) : str ทำหน้าที่อะไรในระบบ 2 คะแนน

2) เหตุใด CreditCardPayment และ PromptPayPayment จึงเสียบเข้ากับ Gateway เดียวกันได้ สอดคล้องกับแนวคิดใด 2 คะแนน

3) ลูกศร “injected” จาก PaymentGateway ชี้ไปยัง PaymentMethod หมายถึงอะไร และเหตุใด Gateway จึงห้ามสร้าง object วิธีชำระเงินเองภายใน 2 คะแนน

4) ลูกศร “raises” ชี้ไปยัง ValueError หมายถึงการตรวจสอบใด และอยู่ในเมธอดใด 1 คะแนน

5) หากเพิ่มช่องทางชำระ TrueMoney Wallet ในอนาคต โค้ดส่วนใดต้องแก้ไขบ้าง (OCP) 2 คะแนน

6) พารามิเตอร์ card_last4: str = "0000" ที่เป็นค่าเริ่มต้นมีประโยชน์อย่างไร 1 คะแนน

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

from abc import ABC, abstractmethod


class PaymentMethod(ABC):
    @abstractmethod
    def pay(self, amount: float) -> str: ...


class CreditCardPayment(PaymentMethod):
    def __init__(self, card_last4: str = "0000"):
        self._card_last4 = card_last4

    def pay(self, amount: float) -> str:
        return f"ชำระ {amount:.2f} บาทด้วยบัตรเครดิต ****{self._card_last4}"


class PromptPayPayment(PaymentMethod):
    def pay(self, amount: float) -> str:
        return f"ชำระ {amount:.2f} บาทด้วย PromptPay"


class PaymentGateway:
    def __init__(self, method: PaymentMethod):
        self._method = method

    def checkout(self, amount: float) -> str:
        if amount <= 0:
            raise ValueError("Amount must be positive.")
        return self._method.pay(amount)


gateway = PaymentGateway(PromptPayPayment())
print(gateway.checkout(1500.00))

1) บรรทัดใดแสดง Dependency Injection จงอธิบาย 2 คะแนน

2) ผลลัพธ์ของ gateway.checkout(1500.00) ในโค้ดบรรทัดสุดท้ายคืออะไร 3 คะแนน

3) หากเรียก gateway.checkout(-100) จะเกิดอะไรขึ้น เพราะเหตุใด 2 คะแนน

4) หากภายใน checkout มีโค้ด return CreditCardPayment().pay(amount) โดยตรง จะผิดหลักการใด และส่งผลเสียอย่างไร 3 คะแนน

ส่วนที่ 5: สะท้อนคิดเชิงออกแบบ OOAD (6 คะแนน)

1) ระบบนี้แสดง Protected Variations อย่างไร “จุดที่เปลี่ยนแปลง” คืออะไร และถูกปกป้องด้วยกลไกใด 2 คะแนน

2) การพึ่งพา ABC (PaymentMethod) แทน concrete class ดีกว่าอย่างไรในแง่การทดสอบด้วย Fake/Mock 2 คะแนน

3) หากมหาวิทยาลัยเพิ่มนโยบาย “ผ่อนชำระค่าเทอม 3 งวด” นักศึกษาจะออกแบบส่วนเพิ่มเติมอย่างไร โดยไม่ต้องแก้ PaymentGateway 2 คะแนน
