Feeling รายงาน audit ที่ถูกตีกลับเพราะ “เวลาผิดความหมาย”

สัปดาห์ก่อนประกาศผลกิจกรรมชมรม ทีม A และทีม B รวมโค้ดเข้าด้วยกัน ทีม A มี mixin บันทึก “เวลาสร้างเอกสาร” ทีม B มี mixin บันทึก “เวลาตรวจสอบเอกสาร” — ทั้งสองตั้งชื่อเมธอดว่า timestamp() เหมือนกันแต่ความหมายต่างกัน พอรวมคลาส Document ที่สืบทอดทั้งสอง mixin Python ไม่พังและไม่เตือนอะไรเลย แต่เลือกตาม MRO ให้เอง — ผลคือรายงาน audit แสดง “เวลาสร้าง” ในช่อง “เวลาตรวจสอบ” ผู้ตรวจสอบตีกลับรายงานทั้งฉบับ และทีมต้องค้างคืนเพื่อตามหาต้นตอ

1) คุณรู้สึกอย่างไรกับเหตุการณ์นี้ และความผิดพลาดนี้เป็นของ “คนตั้งชื่อ” หรือของ “การออกแบบที่ไม่มีกติกาประกาศความกำกวม” มากกว่ากัน

2) ทำไม Python จึงไม่ “เดา” หรือพังเสียงดังแบบ PHP (Fatal Error) แต่เลือกเงียบ ๆ ตาม MRO — คุณว่าแบบนี้ดีหรืออันตรายกว่ากัน เพราะเหตุใด

เรื่องเล่าจากพี่เลี้ยง: “30 คลาสที่คัดลอกพฤติกรรมเดียวกัน”

พี่ไอซ์ — Senior Engineer ใน software house เล่าว่าพฤติกรรมเล็ก ๆ อย่าง timestamp / audit log / soft delete ถูก copy-paste กระจายอยู่ใน 30 คลาส วันที่กฎหมายกำหนดให้ทุกเอกสารต้องมี audit log ทีมต้องไล่แก้ 30 แห่งและพลาดไป 3 แห่ง — ผลคือถูกปรับในการ audit ปลายปี หลังวิกฤตเธอรวมพฤติกรรมร่วมไว้ใน mixin และตั้งกติกาทีมว่า “ทุกครั้งที่ประกอบ mixin ที่มีชื่อชน ต้องประกาศลำดับ MRO และเขียนเมธอดเรียกชัด ๆ สำหรับอีก implementation เสมอ” ตั้งแต่นั้นการเพิ่มพฤติกรรมใหม่แก้เพียงที่เดียว และไม่มี collision หลุดไปถึง production อีกเลย “ความกำกวมที่ระบบยอมให้ผ่าน คือหนี้ที่ทีมจะต้องจ่ายตอนตีหนึ่ง”

ถอดรหัสวิธีคิดของคนสำเร็จ:

  • รวมพฤติกรรมร่วมไว้ในที่เดียว (DRY) — เขียนครั้งเดียว ใช้ได้หลายคลาส
  • แยกแต่ละ concern ออกจากกันเป็น mixin ละเรื่อง (Separation of Concerns)
  • เมื่อชื่อชนกัน ต้องประกาศกติกาชัดด้วยลำดับ MRO + เมธอดเรียกชัด ๆ — อย่าปล่อยให้เลือกเอง
  • ไม่ใช้ mixin พร่ำเพรื่อจนพฤติกรรมของคลาสกระจัดกระจายติดตามยาก

Finding Sandbox: ความกำกวมที่ Python ไม่ยอมเดาให้ดัง ๆ

ทัศนคติประจำใบงาน: Failure is learning — ความเงียบในสนามซ้อมดีกว่าความเงียบในระบบจริง

พิจารณาโค้ดต่อไปนี้ แล้วทำนายว่า Python จะตอบว่าอย่างไร

from datetime import datetime

class Timestampable:
    def timestamp(self) -> str:
        return "Created: " + datetime.now().isoformat()

class Auditable:
    def timestamp(self) -> str:
        return "Audited: " + datetime.now().isoformat()

class Document(Timestampable, Auditable):
    pass   # ไม่ประกาศกติกาใด ๆ! Python เลือกเงียบ ๆ ตาม MRO


doc = Document()
print(doc.timestamp())   # "Created: ..." — แต่รายงาน audit ต้องการ "Audited"!

1) เหตุใด Python จึงพิมพ์ “Created:” ทั้งที่รายงาน audit ต้องการ “Audited:” และไม่พ่น error เหมือน PHP — การ “เลือกให้เงียบ ๆ” อันตรายอย่างไรในระบบทะเบียนหรือการเงิน

2) หากคุณเป็นคนออกแบบกติกา คุณจะประกาศอย่างไรให้ (ก) มี timestamp หลักเพียงหนึ่งความหมาย และ (ข) ยังเข้าถึง implementation ของอีก mixin ได้เมื่อต้องการ

3) ลองให้ AI เสนอวิธีแก้ mixin method collision มา 3 วิธี แล้วถกกับเพื่อน: วิธีใดน่าเชื่อถือที่สุด และคำตอบของ AI เชื่อถือได้มากน้อยเพียงใด (ฟังเพื่อนให้จบก่อนสรุปนะ)

📦 กล่องความรู้เสริม (อ่านเฉพาะเมื่อจำเป็น):
  • Mixin: คลาสที่ออกแบบมาเพื่อ “เติมพฤติกรรม” ให้คลาสอื่นผ่านการสืบทอดแบบหลายทาง สร้าง instance เองไม่ได้
  • MRO (Method Resolution Order): เมธอดของ base class ที่อยู่ก่อนในวงเล็บจะชนะ — ตรวจลำดับได้จาก Document.__mro__
  • เทียบ PHP: ลำดับ base class ≈ insteadof; เมธอดเรียกชัด ๆ Auditable.timestamp(self) ≈ as alias
  • DRY + Separation of Concerns: พฤติกรรมร่วมเขียนครั้งเดียว และแยกแต่ละ concern เป็น mixin ละเรื่อง
  • กติกาทีม: เมื่อชื่อชนกัน ต้องประกาศลำดับ MRO และ alias/เมธอดเรียกชัด ๆ เสมอ — อย่าปล่อยให้เลือกเอง

ส่วนที่ 1: อ่านแผนภาพแล้วตอบคำถาม (10 คะแนน)

1) “Mixin” ใน Python คืออะไร และแตกต่างจากการสืบทอดแบบปกติอย่างไร 2 คะแนน

2) เมื่อ Document สืบทอดทั้ง Timestampable และ Auditable ซึ่งมี timestamp() ชนกัน Python ตัดสินใจอย่างไรว่าเมธอดของคลาสใดถูกใช้ (MRO คืออะไร) 2 คะแนน

3) ป้าย “MRO wins (insteadof)” บนลูกศรไปยัง Timestampable หมายถึงอะไร และเทียบได้กับคำสั่งใดของ PHP 2 คะแนน

4) ลูกศรประ “audit_timestamp alias” หมายถึงอะไร และเทียบได้กับ keyword ใดของ PHP 2 คะแนน

5) หลังแก้ conflict แล้ว Document มีเมธอดใดให้ใช้งานบ้าง จง liệt kê ตามแผนภาพ 1 คะแนน

6) การใช้ Mixin ในข้อนี้สอดคล้องกับหลัก DRY และ Separation of Concerns อย่างไร 1 คะแนน

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

from datetime import datetime


class Timestampable:
    """Mixin: เวลาที่สร้างเอกสาร"""
    def timestamp(self) -> str:
        return "Created: " + datetime.now().isoformat()


class Auditable:
    """Mixin: เวลาตรวจสอบ + ข้อความ audit"""
    def timestamp(self) -> str:
        return "Audited: " + datetime.now().isoformat()

    def audit_message(self) -> str:
        return "Student document was audited."


class Document(Timestampable, Auditable):
    # ลำดับ base class ทำหน้าที่เหมือน insteadof:
    # timestamp() ของ Timestampable ชนะตาม MRO
    def audit_timestamp(self) -> str:
        # ทำหน้าที่เหมือน alias: เรียก implementation ของ Auditable ชัดเจน
        return Auditable.timestamp(self)

    def created_at(self) -> str:
        return self.timestamp()

    def audit_log(self) -> str:
        return f"{self.audit_timestamp()} | {self.audit_message()}"


doc = Document()
print(doc.created_at())
print(doc.audit_log())
print(Document.__mro__)

1) การเรียก doc.created_at() ให้ผลลัพธ์ขึ้นต้นด้วยคำว่าอะไร เพราะใช้ timestamp() ของ mixin ใด และเพราะเหตุใด 3 คะแนน

2) การเรียก doc.audit_timestamp() ให้ผลลัพธ์ขึ้นต้นด้วยคำว่าอะไร ทั้งที่เมธอดนี้ไม่มีอยู่ใน mixin ใดเลย 3 คะแนน

3) หากสลับลำดับเป็น class Document(Auditable, Timestampable) ผลลัพธ์ของ timestamp() จะเปลี่ยนไปอย่างไร เพราะเหตุใด 2 คะแนน

4) เหตุใดจึงไม่ควรใช้ Mixin พร่ำเพรื่อจนพฤติกรรมของคลาสกระจัดกระจาย จงอธิบายด้วยหลัก Separation of Concerns 2 คะแนน
